# 录音直转笔记：产品需求与高保真原型稿

> 文档状态：方案评审稿
>
> 目标：在现有“多媒体笔记工作台”中增加“点击录音，停止后直接转化为笔记”的能力。
>
> 约束：本稿只做产品设计、交互原型和研发交接，不修改现有代码。

## 1. 结论先行

建议把新能力落在现有 `/audio-notes` 录音入口内，并在首页增加一个更短的“开始录音”快捷入口。MVP 采用以下链路：

```mermaid
flowchart LR
  A[点击开始录音] --> B[浏览器麦克风授权]
  B --> C[本地录音中]
  C --> D[点击完成并试听]
  D --> E[上传录音文件]
  E --> F[复用现有 NoteJob]
  F --> G[转写]
  G --> H[生成并审核笔记]
  H --> I[写入当前连接器]
  I --> J[笔记 + 原始转录 + 转化记录]
```

MVP 明确是“录完即转化”，不是“边说边出字幕”。当前项目的媒体任务采用 HTTP 创建任务、短轮询获取进度，后端已有 `sourceType: audio`、转写、摘要、原文归档和转化记录能力；因此先把浏览器 `MediaRecorder` 产出的完整音频接入现有任务链，风险最低、复用率最高。

实时字幕、多人说话人识别、边录边生成行动项属于 P1/P2，不应在第一版用假进度或假字幕冒充。

## 2. 当前项目证据与影响范围

### 已存在的能力

| 证据 | 当前行为 | 对新功能的含义 |
| --- | --- | --- |
| `client/src/pages/AudioNotesPage/AudioNotesPage.tsx` | 复用 `MediaNotePage`，只能选择音频文件 | 新入口应与现有上传并列，不能破坏上传流程 |
| `MediaNotePage` | 已有上传、取消、进度、失败、原始转录和笔记链接 | 录音结束后的任务状态可直接沿用 |
| `shared/api.interface.ts` | 已有 `NoteSourceType: audio`、`CreateNoteJobRequest`、`NoteJob`、`NoteConversionRecord` | 不需要新建另一套“会议任务”对象 |
| `server/modules/note-jobs` | 已支持音频转写、摘要生成、发布和短轮询状态 | 录音文件完成上传后可复用同一流水线 |
| `ConversionHistoryPage` | 已按录音筛选并展示处理状态、原文、笔记和源文件 | 新记录需标记“麦克风录音”来源 |
| `TranscriptionSettingsPage` | 腾讯云 ASR / 本地 Whisper 二选一，支持说话人分离配置 | 录音前只需展示当前转录引擎状态，不要重复配置 |
| `README.md` / `docs/PROJECT_GUIDE.md` | 本地音频支持 10 GB；当前异步任务保存在进程内存 | 浏览器录音不能照搬 10 GB 上限，需单独设置录音时长和恢复边界 |

### 变更影响分析

- 影响模块：入口页、录音页、媒体上传适配、NoteJob 元数据、转化记录展示、操作手册。
- API：MVP 可复用现有创建音频任务接口；建议增加录音来源元数据，而不是另造一条处理 API。
- 数据结构：建议新增可选的 `captureMode` 与 `recordingMeta`，保持旧上传记录兼容。
- 向后兼容：`captureMode` 缺省视为 `file_upload`；现有音频上传、视频、文档和双源任务不变。
- 风险等级：中。浏览器权限、长时间录音内存、页面刷新丢失是主要风险。
- 回滚：关闭首页“开始录音”入口并保留 `/audio-notes` 上传入口即可；历史记录中的可选元数据不影响旧任务读取。

## 3. 用户与场景

### 目标用户

- 会议后想快速得到纪要的人。
- 课堂、访谈、调研现场需要先记录、后整理的人。
- 不想先打开系统录音 App、再导入文件的个人用户。

### 核心场景

1. 会议开始前：点击“开始录音”，输入标题，结束后生成会议纪要。
2. 课堂中：录音过程中点击“标记重点”，课后在笔记中看到重点时间点。
3. 访谈后：试听确认声音完整，再选择“学习笔记”或“会议纪要”。
4. 权限受限：用户拒绝麦克风时，仍能回到“上传录音”路径。

### 非目标

- 第一版不做多人实时在线会议室。
- 第一版不做边录边显示真实转写字幕。
- 第一版不做自动判断发言人姓名。
- 第一版不把麦克风音频自动同步到云端，录音结束前不上传。

## 4. 方案取舍

| 方案 | 说明 | 复用现有能力 | 体验 | 技术风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 录完即转化 | 浏览器录音，停止后上传 Blob，复用音频 NoteJob | 高 | 简洁、可解释 | 中 | **MVP 推荐** |
| B. 边录边上传，停止后合并 | 录音分片上传，服务端持续保存，结束后合并 | 中 | 可支持超长录音和恢复 | 高 | P1 |
| C. 实时 ASR + 实时纪要 | WebSocket/WebRTC 或厂商实时 ASR，边说边出字幕 | 低 | 最接近飞书/腾讯会议 | 很高，且偏离当前 HTTP-only 架构 | P2 |

### 推荐理由

方案 A 不改变当前后端“创建任务 + 短轮询”的主模型，也不需要新增 WebSocket。录音结束前没有网络上传，隐私边界清晰。为避免浏览器内存随录音时间增长，MVP 需设置时长上限并在界面明确说明；超过上限再进入方案 B。

## 5. 信息架构与入口

### 首页入口调整

在当前首页五类素材入口中，将“录音笔记”升级为两种动作：

- 主动作：`开始录音`，进入录音态。
- 次动作：`上传录音文件`，保留现有 `/audio-notes` 文件上传流程。

不建议在全局 Layout 中放一个长期悬浮录音按钮。录音是高风险权限动作，入口应有明确上下文、标题和状态，避免误触。

### `/audio-notes` 页面结构

顶部保留当前项目的返回入口、绿色音频主题和处理阶段条；右侧任务面板在未开始时改为二段式：

```text
录音整理工作台                                      返回入口
上传、转录、总结、发布

让一段录音，沉淀成真正可复习的笔记。

┌──────────────────────────────────────────────┐
│  ● 直接录音                                    │
│  点击开始，结束后自动转写并生成笔记             │
│                                                │
│  [ 麦克风图标 ]      [ 开始录音 ]              │
│                                                │
│  或                                            │
│  [ 上传录音文件 ]                               │
│  支持 MP3、M4A、WAV、AAC、FLAC、OGG             │
└──────────────────────────────────────────────┘
```

默认焦点落在“开始录音”，但不自动请求麦克风权限；只有用户点击后才触发浏览器授权。

## 6. 高保真原型稿

以下规格按当前项目视觉语言编写：`#f7f7f5` 页面底色、白色任务面板、音频主题 `#168b75`、浅绿 `#eaf8f4`、细边框、8–32px 圆角、Lucide 图标、中文优先的紧凑排版。

### Screen 0：录音入口（默认态）

**目的**：让用户 3 秒内理解“可以直接录音”，同时保留文件上传。

| 区域 | 规格 |
| --- | --- |
| 页面标题 | `让一段录音，沉淀成真正可复习的笔记。` |
| 主卡片 | 白底，`border-radius: 32px`，内边距 32px，顶部对齐当前处理阶段 |
| 主动作 | 绿色实心按钮，48px 高，文案 `开始录音`，图标 `Mic` |
| 次动作 | 白底描边按钮，44px 高，文案 `上传录音文件`，图标 `UploadCloud` |
| 状态文案 | `录音只在你点击完成后上传处理`，避免误解为实时云端录音 |
| 配置摘要 | `当前转录：本地 Whisper / 腾讯云 ASR`；点击进入既有转录设置 |
| 隐私提示 | `麦克风权限仅用于本次录音；完成前不会上传音频` |

**空态验收**：没有权限、没有录音文件时，主按钮仍可点击；不能因为处理环境未就绪而把“开始录音”置灰。录音结束后再对转写/模型就绪状态做阻塞提示。

### Screen 1：录音准备（权限前）

**目的**：在真正录音前完成最小配置，避免录完才发现输出类型不对。

```text
< 返回录音入口

准备录音
先确认标题和笔记类型，麦克风权限只会在点击下一步时请求。

标题（可选）
[ 例如：产品周会 2026-08-25                         ]

笔记类型
[ 会议纪要 ]  [ 学习笔记 ]

输出位置
● 当前连接器：飞书      [查看配置]

录音上限：90 分钟   文件在完成前仅保存在当前浏览器会话

                         [取消] [允许麦克风并开始]
```

默认标题规则：`录音笔记 · YYYY-MM-DD HH:mm`。默认笔记类型沿用用户上次选择，但第一次使用默认“会议纪要”。

### Screen 2：录音进行中

**目的**：让用户确信正在录音，并能低认知负担地暂停、标记重点和结束。

```text
录音中                                             会议纪要
产品周会 2026-08-25

                 00:18:42
              ● 正在录音

  ▁▂▃▅▆▅▃▂▁▂▃▅▃▂▁▂▃▆▅▃▂▁▂▃▅▆▃▂▁

 [标记重点]                  [暂停]   [完成录音]

 麦克风：内置麦克风 · 声音正常
 已标记 3 个重点 · 完成后会出现在原始转录时间点
```

交互要求：

- 计时器使用 `mm:ss`，超过 60 分钟显示 `hh:mm:ss`，使用等宽数字。
- 声波是输入音量的可视反馈，不承诺是转写结果；无输入时显示“未检测到声音”。
- “完成录音”是唯一主结束动作；点击后进入试听确认，不直接提交，避免误触丢失。
- “暂停”后继续使用同一录音会话，按钮文案切换为 `继续录音`。
- `标记重点` 使用图钉图标和短暂 toast，不弹出输入框打断录音；可选备注在结束后补充。
- 录音中禁止路由离开，离开前必须弹出确认；刷新/关闭页面要触发浏览器 `beforeunload` 提示。

### Screen 3：暂停态

```text
已暂停                                           00:18:42
录音内容仍保留在当前会话中

               [继续录音]
               [完成录音]
```

暂停态不应显示“处理中”，避免用户误以为系统已经开始转写。页面刷新、浏览器崩溃后的恢复属于 P1；MVP 至少要在离开页面时二次确认。

### Screen 4：结束试听与提交

**目的**：给用户一个可逆的最后检查点。

```text
录音完成
产品周会 2026-08-25 · 18 分 42 秒

[▶ 00:00 ─────────────── 18:42 🔊]

录音质量
✓ 已检测到有效声音
! 约 2 分钟音量偏低（建议生成后核对）

笔记类型       [会议纪要 ▾]
标题           [产品周会 2026-08-25                 ]
重点标记       3 个 · 00:04:12 / 00:09:31 / 00:16:05

                [重新录音] [开始转化为笔记]
```

“开始转化为笔记”提交后，先把 Blob 转成现有 `UploadedMediaInput`，再创建 `sourceType: audio` 任务。提交按钮显示 `上传并开始转化`，不能使用“实时生成”之类误导文案。

### Screen 5：上传与处理

复用现有处理页样式和阶段条，新增录音专属信息：

1. `准备录音文件`
2. `安全上传`
3. `语音转文字`
4. `生成笔记`
5. `写入飞书`

阶段卡片下方显示：

- 录音标题、时长、文件大小。
- `录音来源：麦克风录音`。
- 当前转录引擎与说话人分离是否开启。
- `停止处理`；停止后保留已完成的本地录音，可再次提交。

### Screen 6：结果页

沿用现有完成态，但增加双入口和重点回看：

```text
笔记已经准备好
产品周会 2026-08-25 · 麦克风录音 · 18 分 42 秒

✓ 飞书文档创建成功

[打开总结笔记 ↗]
[查看原始转录 ↗]
[下载原文 ↓]

重点标记
00:04:12  需求范围确认
00:09:31  发布日期待定
00:16:05  行动项分工

[再录一段] [返回录音入口]
```

若当前连接器是本地或钉钉，沿用连接器文案，不硬编码飞书。

### Screen 7：权限拒绝与设备异常

| 场景 | 页面文案 | 主动作 | 次动作 |
| --- | --- | --- | --- |
| 用户拒绝麦克风 | `无法访问麦克风，请在浏览器地址栏允许麦克风权限后重试。` | `重新请求权限` | `上传录音文件` |
| 无可用设备 | `没有检测到可用麦克风，请连接设备后重试。` | `重新检测` | `上传录音文件` |
| 录音中无声音 | `暂未检测到声音，仍可继续录音。` | `继续录音` | `完成录音` |
| 浏览器不支持 | `当前浏览器不支持直接录音，请使用最新版 Chrome、Edge 或 Safari。` | `查看支持说明` | `上传录音文件` |
| 转写环境未就绪 | `录音已保留，但当前转写环境未就绪。` | `去配置转录` | `稍后处理` |
| 上传失败 | `录音仍在本机会话中，可重试上传。` | `重试上传` | `重新录音` |

错误态不得清空录音 Blob；用户在本次页面会话中至少有一次重试机会。

### Screen 8：转化记录

在现有记录行增加：

- 来源徽标：`麦克风录音`，与 `录音文件` 区分。
- 时长、录音质量警告数量、重点标记数量。
- 操作菜单：打开笔记、打开原文、下载原文、再次生成。

筛选仍使用现有“录音”来源筛选；新增来源渠道筛选项可选，不应改变旧查询参数语义。

## 7. 功能需求

### P0 必须有

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| REC-01 | 从首页和 `/audio-notes` 进入开始录音 | 两处入口均能到达准备态；不影响上传录音 |
| REC-02 | 点击后请求麦克风授权 | 页面加载不请求权限；拒绝后给出恢复路径 |
| REC-03 | 开始、暂停、继续、完成 | 计时准确；暂停不丢数据；完成后进入试听确认 |
| REC-04 | 录音质量反馈 | 展示有无声音；不把音量反馈描述成转写 |
| REC-05 | 试听和重录 | 完成后可播放、重新录音或提交；重录不覆盖未提交会话，除非用户确认 |
| REC-06 | 录音转现有 NoteJob | 提交后出现上传、转写、生成、发布阶段；可轮询到完成/失败 |
| REC-07 | 选择会议纪要/学习笔记 | 默认会议纪要；选择结果传入现有模板选择逻辑 |
| REC-08 | 原始转录和总结笔记可回看 | 结果页、转化记录均可打开现有链接 |
| REC-09 | 失败可恢复 | 权限、设备、上传、转写失败均保留明确的重试或上传替代路径 |
| REC-10 | 隐私告知 | 完成录音前不上传；页面明确当前录音保存在浏览器会话中 |

### P1 建议有

- 录音中上传分片，支持 90 分钟以上录音和断点恢复。
- 标记重点可补充一句短备注，并写入原文时间锚点。
- 录音前选择输入设备、采样率和声道；普通用户默认隐藏高级项。
- 结果页点击重点跳转到对应音频时间点。
- 页面刷新后恢复未提交录音（IndexedDB）。

### P2 后续再做

- 实时字幕、实时摘要和实时行动项。
- 多人说话人分离与自定义姓名。
- 会议中途邀请参与者、共享链接、主持人权限。
- 与飞书会议/腾讯会议的会议元数据同步。

## 8. 建议的数据与接口契约（设计层）

MVP 不新增独立“录音任务”资源，建议让现有音频任务可表达录音来源：

```ts
// 建议的可选字段，旧上传任务不受影响
type CaptureMode = 'file_upload' | 'microphone';

interface RecordingMeta {
  durationMs: number;
  inputDeviceLabel?: string;
  markerCount: number;
  markers: Array<{ atMs: number; note?: string }>;
  mimeType: string;
  qualityWarnings: string[];
}
```

建议在创建任务请求和历史记录中增加可选的 `captureMode`、`recordingMeta`；后端落库时保持空值兼容。录音 Blob 仍转换为现有 `UploadedMediaInput`，避免另造文件存储协议。

当录音时长超过浏览器内存安全阈值时，前端应在提交前阻止继续录音并解释原因；P1 再引入“分片上传会话”接口。不要先把实时 WebSocket 设计塞进当前 HTTP-only 的接口边界。

## 9. 非功能要求

- 录音开始、暂停、完成、重试均可通过键盘操作；按钮有可读的 `aria-label`。
- 颜色不能作为唯一状态提示；录音状态同时使用图标、文字和计时器。
- 手机窄屏下主操作固定在可见区域，按钮最小触控高度 44px。
- 录音页面切后台时显示“仍在录音”状态；浏览器不支持后台录音时在准备态说明。
- 关闭页面前提示未提交录音；不在日志输出原始音频、Blob、麦克风设备标识或密钥。
- 所有 AI 转写和笔记都标记为需要人工核对，沿用当前项目的证据边界。

## 10. 验收场景

1. 首次点击“开始录音”，允许权限，录 10 秒，试听并提交，最终生成音频类型转化记录。
2. 拒绝权限，页面给出重新授权和上传文件两个可用动作。
3. 录音中暂停 5 秒再继续，最终音频时长不包含暂停时长或在产品定义中明确包含规则；建议采用“不计入暂停时长”。
4. 录音中点击 3 次重点，结果页和原文中出现 3 个时间点。
5. 提交前重录，旧 Blob 被用户确认后丢弃；未确认前不静默覆盖。
6. 上传失败后重试，不要求重新录音。
7. 转写环境未就绪，录音保留并可稍后处理；不显示虚假的“已生成”。
8. 刷新转化记录，麦克风录音与文件上传都出现在“录音”筛选中，来源文案可区分。
9. 现有上传录音、视频、文档和双源任务回归通过。
10. 服务重启后，已创建的任务按当前项目能力给出明确的不可恢复提示；未承诺 P1 前的断点恢复。

## 11. 视觉与设计交接

### 选用设计系统

- 基线：当前项目现有的 neutral-modern 视觉语言，而不是新引入一套会议 SaaS 风格。
- 音频强调色：`#168b75`；浅色背景：`#eaf8f4`；页面底色：`#f7f7f5`。
- 组件：沿用 Lucide 图标、shadcn Button/Progress/Dialog、现有卡片和阶段条。
- 录音态只增加一个“状态层”：绿色表示正常录音，琥珀表示无声/需注意，红色表示设备或权限错误。

### 高保真视觉验收

- 桌面端 1440px：准备态左侧说明、右侧任务面板；录音态计时器和主操作位于首屏中心。
- 移动端 390px：标题不截断主意图；完成录音按钮始终位于首屏下方可见区域；底部操作不遮挡状态信息。
- 录音态不使用大面积动画或渐变；声波动画仅作为输入反馈，帧率低时仍显示静态音量条。
- 所有按钮有图标和文字，陌生图标提供 tooltip；“停止”使用 `Square` 图标，“开始”使用 `Mic` 图标。

### Open Design 交接信息

- 设计目标：在不改变现有媒体笔记工作台信息架构的前提下，把“开始录音”压缩为一个可信、可恢复的短路径。
- 仓库文档依据：`README.md`、`docs/PROJECT_GUIDE.md`、`docs/OUT_OF_BOX_AUDIT.md`、现有 `AudioNotesPage`、`MediaNotePage`、`ConversionHistoryPage` 和共享接口定义。
- Impeccable：未使用。当前已有明确的视觉系统和页面实现，首要任务是扩展交互状态，不是重做品牌设计。
- Open Design 工作台：当前环境未提供已批准的 `OPEN_DESIGN_URL`，因此本稿不生成或虚构可点击项目 URL。
- 设计提示词：`Create a high-fidelity responsive recording-to-note flow inside the existing Media Notes Workbench. Preserve the current neutral off-white background, white rounded task panel, teal audio accent #168b75, compact Chinese typography, Lucide icons, and existing upload/progress/result patterns. Design states: entry, permission preflight, recording, paused, finish-preview, processing, success, permission error, upload error. Make the main action explicit and reversible; do not show fake real-time transcription in the MVP.`

## 12. 研发拆分建议

1. **交互壳层**：录音状态机、权限处理、计时器、暂停/继续、完成试听、离开拦截。
2. **媒体适配**：`MediaRecorder` MIME 选择、Blob 转 `UploadedMediaInput`、录音大小/时长校验。
3. **任务接入**：复用音频 NoteJob 创建、轮询、取消、结果页和错误恢复。
4. **元数据**：录音来源、时长、重点标记、质量告警写入历史记录。
5. **回归验证**：现有文件上传、转写设置、连接器切换、转化记录筛选和移动端布局。

## 13. 最终决策门

研发开始前只需要确认三件事：

1. MVP 是否接受“停止后才转写”，不做实时字幕。
2. 首版录音时长上限取 60 分钟还是 90 分钟；建议 90 分钟，并在接近上限时提醒。
3. 录音结果默认使用“会议纪要”模板，还是沿用用户最近一次选择；建议首次默认会议纪要，之后记忆用户选择。
