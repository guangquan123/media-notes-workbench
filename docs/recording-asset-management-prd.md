# 录音资产持久化与记录管理需求规格书

文档状态：需求评审稿
版本：v1.0
日期：2026-09-04
范围：录音结束后的自动保存、可配置本地归档目录、录音记录管理，以及与现有转写/笔记任务的衔接
本轮结论：只做需求设计，不开发

## 1. 摘要与决策

当前问题不是“录音按钮不够好用”，而是录音资产的生命周期没有闭环：录完后如果暂不处理，用户不知道录音在哪里；页面刷新、服务重启或路径不可用时，录音可能无法继续处理；已有转化记录主要围绕 NoteJob，不能独立管理“尚未转为笔记”的录音。

建议新增“录音资产中心”，把录音文件作为独立、可追溯的一级对象：

1. 录音停止后立即生成录音资产记录，并先写入应用可恢复存储。
2. 用户可在本地运行模式下配置一个电脑目录，系统在录音完成后自动复制/移动音频到该目录；目录不可用时不阻断录音，保留应用内副本并提示待归档。
3. 录音资产可以单独播放、重命名、下载、归档、删除、重新转写或生成笔记。
4. 转写和笔记任务继续复用现有 `NoteJob` 与 `ConversionHistory`，通过 `recordingAssetId` 关联，而不是再创建一套平行任务模型。

### 1.1 关键产品判断

| 判断 | 结论 |
| --- | --- |
| 网页能否静默写入任意电脑路径 | 不能。浏览器必须经过用户选择目录并授予权限，或由本地后端/桌面容器代写。 |
| 是否应该把“本地目录保存”作为唯一保存方式 | 不应该。目录权限、磁盘空间、移动硬盘和网络盘都可能失效，必须有应用内持久化兜底。 |
| 录音与转写是否绑定为一个对象 | 不绑定。录音资产先独立存在，转写/笔记是可重试、可产生多个版本的处理结果。 |
| 记录管理放在哪里 | 新增“录音记录”视图；现有“转化记录”保留，并支持从录音记录进入处理详情。 |

## 2. 当前项目依据与影响分析

### 2.1 已有能力

- `RecordingNotesPage` 已有录音、暂停/继续、完整性检查、IndexedDB 中断恢复和上传后创建音频 `NoteJob` 的流程。
- `recording-storage.ts` 使用 `media-notes-recordings` IndexedDB 保存录音分片，可恢复最近一次未完成录音，但目前不是面向用户的长期录音库。
- `NoteSourceType` 已支持 `audio`，`CreateNoteJobRequest`、`NoteJob` 和 `NoteConversionRecord` 可以承接录音转写与笔记结果。
- `ConversionHistoryPage` 已支持按录音查看处理状态、原始转录、笔记链接和源文件操作。
- 当前部分任务状态保存在进程内存，服务重启后不可依赖其恢复；录音资产不能只挂在内存中的 NoteJob 上。

### 2.2 变更影响

- 影响模块：录音页、录音存储层、录音记录页、转化记录页、NoteJob 元数据、设置页、本地文件服务。
- API：新增录音资产查询/管理接口；创建 NoteJob 时增加可选 `recordingAssetId`，保持现有文件上传请求兼容。
- 数据结构：新增录音资产、归档策略和文件副本状态；旧音频任务没有 `recordingAssetId` 时按“历史导入音频”处理。
- 向后兼容：现有上传音频、视频、文档、PDF 和双源任务流程不改变；`recordingAssetId` 为可选字段。
- 风险等级：中。主要风险是本地文件权限、跨磁盘路径失效、磁盘空间不足、重复归档和隐私泄露。
- 回滚：关闭“自动归档到本地目录”和“录音记录”入口即可；保留现有录音页上传与转化记录。新增字段均为可选，数据库可通过 Git revert 回滚迁移。

## 3. 用户、场景与目标

### 3.1 目标用户

- 会议、课堂、访谈和调研的个人记录者。
- 需要先录音、晚些时候再整理的用户。
- 希望音频文件可以被系统以外的播放器、网盘或备份工具继续使用的用户。

### 3.2 核心场景

1. **录完暂不处理**：用户点击完成录音后离开页面，数小时或数天后仍能从录音记录找到并继续转写。
2. **自动本地归档**：用户已配置 `D:\录音归档\`，录音完成后系统自动保存为可读文件，并在记录中显示实际路径。
3. **路径失效**：移动硬盘未连接或目录无权限，系统保留应用内副本，记录状态为“待归档”，提供重试或另存为。
4. **重新处理**：同一录音先生成会议纪要，后来又生成学习笔记；原始录音和历史结果均保留。
5. **外部录音纳管**：用户导入已有 MP3/M4A/WAV，纳入同一录音记录库，再选择转写或生成笔记。

### 3.3 产品目标

- 录音停止后 100% 先形成可恢复的录音资产记录，不能因转写失败而丢失源音频。
- 用户可在 10 秒内找到最近一次未处理录音，并继续处理或下载。
- 用户可看到每个录音的保存位置、归档状态、处理状态和最新笔记入口。
- 录音、转写、笔记之间保持一对多关系，支持重试和版本追溯。

### 3.4 非目标

- 本阶段不做云端多端同步、多人共享或在线协作。
- 不做实时字幕、说话人姓名识别和音频剪辑混音。
- 不承诺浏览器在用户未授权时直接写入任意目录。
- 不自动删除用户已归档到本地目录的文件，删除策略必须由用户明确选择。

## 4. 核心原则

1. **先保存，后处理**：录音文件落地是停止录音的完成条件，转写只是后续任务。
2. **应用内副本优先于外部路径**：本地目录是归档副本/目标位置，不是唯一事实来源。
3. **状态可解释**：任何“已保存”“待归档”“归档失败”都必须能说明位置、原因和下一步。
4. **源文件与结果分离**：原始音频不可被转写或笔记重试覆盖。
5. **显式授权与最小权限**：目录访问、删除和覆盖均需要用户明确确认。
6. **幂等处理**：重复点击、网络重试或页面重新打开不能生成重复录音资产或重复归档文件。

## 5. 信息架构

### 5.1 导航

在现有入口中增加“录音记录”，与“录音笔记”并列：

```text
首页
├─ 录音笔记：开始录音 / 上传录音并生成笔记
├─ 录音记录：全部录音资产，未处理录音优先
└─ 转化记录：所有媒体转写与笔记任务（含录音关联）
```

### 5.2 录音记录列表

默认排序：未处理和待归档在前，其次按最近更新时间倒序。每条记录展示：

- 标题、录音时间、时长、文件大小、音频格式。
- 资产状态：`已保存`、`待归档`、`归档中`、`已归档`、`归档失败`、`已删除`。
- 处理状态：`未处理`、`处理中`、`已生成笔记`、`处理失败`。
- 当前位置：应用内保存、电脑归档路径或“路径不可用”。
- 快捷操作：播放、继续处理、下载、重命名、更多。

筛选项：状态、处理状态、时间范围、标题关键词、是否已归档。
搜索范围只包含用户可见的标题、文件名和备注，不搜索音频内容。

### 5.3 录音详情页

详情页采用单一任务工作区，不将录音和笔记塞进同一张卡片：

1. 音频播放器与基础元数据。
2. 保存位置与归档状态。
3. 处理入口：转写、生成会议纪要、生成学习笔记、重新处理。
4. 处理历史：按版本列出 NoteJob、转写稿、笔记链接、失败原因和创建时间。
5. 危险操作：删除应用内副本、解除本地归档关联；删除本地文件需单独确认。

## 6. 功能需求

### 6.1 自动保存与资产生成（P0）

#### 6.1.1 停止录音后的顺序

```text
停止录音
  → 完整性检查
  → 写入应用内持久化存储
  → 创建录音资产记录
  → 尝试本地目录归档（如已配置）
  → 展示“已保存，可稍后处理”
```

- 应用内持久化成功前，不允许页面将录音标记为完成。
- 归档失败不得回滚应用内保存，也不得删除 Blob/分片。
- 用户可在保存完成后关闭页面；转写不自动开始，除非用户在录音设置中开启“录完自动生成笔记”。
- 录音资产生成使用客户端会话幂等键，重复提交返回同一资产。

#### 6.1.2 录音完成页

- 主按钮：`稍后处理`，返回录音记录并保留资产。
- 次按钮：`转为笔记`、`下载录音`。
- 明确显示：`录音已保存`、保存位置、归档状态和可继续处理时间。
- 转写失败时保留“返回录音记录”和“重新提交”，不能只显示失败 toast。

### 6.2 本地归档目录配置（P0/P1）

#### 6.2.1 配置入口

位置：设置 > 录音存储。

字段与规则：

| 字段 | 规则 |
| --- | --- |
| 自动归档 | 开关，默认关闭或按部署策略预设；开启前必须先选择目录。 |
| 归档目录 | 本地模式显示“选择文件夹”；禁止手填后直接假定路径可写。 |
| 文件命名模板 | 默认 `{YYYY-MM-DD}_{HH-mm}_{title}_{assetId8}`；非法字符替换为 `-`。 |
| 冲突策略 | 默认“保留新文件并追加序号”；可选“跳过并标记冲突”，禁止默认覆盖。 |
| 归档动作 | 默认“复制到归档目录并保留应用内副本”；删除应用内副本属于高级选项，默认关闭。 |
| 空间预警 | 归档前检查可用空间，低于配置阈值时提示；失败不影响应用内副本。 |

#### 6.2.2 平台实现边界

- 本地运行模式：由本地后端/桌面能力执行文件复制，前端只展示授权目录和结果。
- 纯浏览器模式：使用 File System Access API 的用户选目录句柄；不支持时降级为“下载到默认下载目录”或“手动下载”。
- 网络盘、移动硬盘、同步盘按普通目录处理，但必须在每次归档前验证可写性。
- 不保存完整访问令牌或目录外的路径信息；展示路径时可按产品隐私策略隐藏用户名段。

#### 6.2.3 归档状态机

```text
未配置 → 不归档
已配置 → 归档中 → 已归档
                  ↘ 归档失败 → 重试 / 另存为 / 保留应用内
已归档 → 路径失效 → 待归档
```

### 6.3 录音记录管理（P0）

- 列表分页或虚拟滚动，默认支持至少 10,000 条资产记录的查询设计。
- 支持标题搜索、时间筛选和状态筛选；筛选条件可复制为 URL 查询参数。
- 支持批量选择：归档、标记已处理、删除应用内副本。批量删除必须二次确认并展示数量。
- 支持单条重命名，重命名只改资产元数据，不自动改已生成笔记标题。
- 支持“继续处理”：沿用最近一次转录配置，也允许重新选择笔记风格和模型。
- 支持“下载录音”：优先下载应用内源文件；应用内文件缺失但本地归档存在时提示重新关联或另存为。
- 记录删除分为两类：`删除记录`（仅隐藏/软删除）和`删除源文件`（永久删除，需单独确认）。
- 已被 NoteJob 引用的录音不能无提示硬删除；删除前展示关联笔记/任务数量。

### 6.4 与现有转写和笔记结合（P0）

- 从录音记录发起处理时，创建现有 `sourceType: audio` 的 NoteJob，并写入 `recordingAssetId`。
- 现有上传音频若没有资产 ID，可在导入完成后自动创建一个“导入来源”录音资产，或保持历史兼容路径。
- 一个录音资产允许多个处理版本：不同笔记风格、不同转录引擎或人工重试均创建新的 NoteJob/ConversionRecord。
- 转化记录中增加“来源录音”入口，点击可回到录音详情；录音详情中显示对应的转化版本。
- 原始转录、笔记文档链接、转录模型和提示词版本继续使用现有字段；录音资产只保存关联关系和源文件信息。
- 转化失败只改变处理状态，不改变录音资产状态；用户可以从同一资产重新提交。

### 6.5 可选的“录完自动生成”（P1）

- 设置项默认关闭，开启时在录音完成页仍先保存资产，再异步创建 NoteJob。
- 允许用户设置默认笔记风格；录音页可临时覆盖。
- 自动处理失败时必须通知并在录音记录中留下失败原因；不自动重试超过配置次数。
- 页面关闭、服务重启不应使已保存录音丢失；任务恢复依赖持久化的资产和 Job 记录。

## 7. 数据模型（设计契约）

### 7.1 RecordingAsset

```ts
interface RecordingAsset {
  id: string;
  title: string;
  source: 'microphone' | 'file_import';
  mimeType: string;
  fileName: string;
  durationMs: number;
  fileSize: number;
  sha256?: string;
  capturedAt: string;
  createdAt: string;
  updatedAt: string;
  storageStatus: 'app_only' | 'archiving' | 'archived' | 'pending_archive' | 'archive_failed' | 'missing';
  appStorageRef: string;
  archive?: {
    directoryId: string;
    filePath?: string;
    archivedAt?: string;
    lastError?: string;
    copyMode: 'copy' | 'move';
  };
  processingStatus: 'unprocessed' | 'processing' | 'processed' | 'failed';
  deletedAt?: string;
}
```

约束：`appStorageRef` 是应用内部可解析引用，不向前端暴露真实磁盘实现；哈希用于幂等与冲突检测，不作为内容检索索引。

### 7.2 关联关系

```text
RecordingAsset 1 ─── N NoteJob 1 ─── 0..1 NoteConversionRecord
       │
       └── 1..N StorageCopy（应用内副本 / 本地归档副本）
```

## 9. 状态与异常交互

| 场景 | 用户可见状态 | 可执行动作 |
| --- | --- | --- |
| 应用内保存成功、未配置目录 | 已保存到录音记录 | 稍后处理、下载、配置归档目录 |
| 目录写入成功 | 已保存并已归档 | 打开所在目录、播放、处理 |
| 目录不存在/移动盘断开 | 已保存，待归档 | 重试、另存为、继续保留应用内 |
| 无权限 | 已保存，归档失败：没有写入权限 | 重新选择目录、重试 |
| 空间不足 | 已保存，归档失败：空间不足 | 另选目录、下载后清理 |
| 转写失败 | 录音仍然保留，处理失败 | 重新提交、修改配置 |
| 应用内副本缺失 | 记录可见但源文件缺失 | 重新关联本地文件、删除记录 |
| 重复归档请求 | 已有归档文件 | 打开现有文件、生成新副本；禁止静默覆盖 |

页面刷新、浏览器崩溃或服务重启后，录音记录页必须优先展示“待归档/未处理/处理失败”资产，不得只展示已完成笔记。

## 10. 权限、安全与数据治理

- 录音开始前继续遵守麦克风权限和用户主动操作要求。
- 归档目录需用户选择或由管理员预配置；不能通过前端输入任意路径绕过授权。
- 目录访问仅用于写入录音资产，默认不扫描目录内其他文件。
- 删除本地文件前必须显示完整路径、文件名和关联资产数量；支持取消。
- 文件名清理非法字符、限制长度，防止路径穿越；服务端再次校验最终路径必须位于已授权目录下。
- 日志不记录音频内容、目录访问令牌或 SecretKey；错误日志可记录错误码和脱敏后的路径。
- 音频属于可能包含个人信息的内容，设置页需说明本地保存位置、保留期限和删除责任。
- 默认保留策略：应用内副本不自动过期；后续可增加“保存 N 天后提醒清理”，不在 P0 自动删除。

## 11. 非功能要求

- **可靠性**：停止录音到“已保存”之间允许重试；应用内写入成功率目标 >= 99.9%（排除浏览器存储被用户禁用）。
- **性能**：录音记录首屏列表响应目标 < 1 秒（已有索引条件下）；大文件归档必须异步并展示进度。
- **可恢复性**：归档和转写均可重试；失败不删除源文件。
- **幂等性**：同一 `captureSessionId` 或文件哈希重复提交不创建重复资产；用户明确选择“另存副本”除外。
- **兼容性**：桌面本地模式优先支持 Windows；浏览器模式对不支持目录授权的浏览器提供下载降级。
- **可访问性**：状态不能只依赖颜色；删除、归档和处理按钮提供键盘焦点与可读状态。

## 12. 埋点与运营指标（P1）

不采集音频内容，仅记录事件与耗时：

- `recording_asset_created`
- `recording_asset_saved`
- `recording_archive_started/succeeded/failed`
- `recording_asset_recovered`
- `recording_asset_processed`
- `recording_asset_reprocess_submitted`
- `recording_asset_deleted`

核心指标：录音保存成功率、待归档率、归档失败原因分布、录音完成后 24 小时内处理率、处理失败后重试率、录音资产找回耗时、重复资产率。

## 13. 分期与验收

### 13.1 P0：先解决“找不到”和“录完丢失”

- 停止录音后创建持久化录音资产。
- 新增录音记录列表、详情、播放、下载、重命名和继续处理。
- 录音资产与现有 NoteJob/ConversionRecord 关联。
- 处理失败保留源音频，支持重新提交。
- 本地归档设置可保存目录并提供测试、重试和待归档状态；至少实现本地模式或明确的下载降级。

### 13.2 P1：自动化与可观测性

- 录完自动生成笔记开关。
- 异步归档进度、批量归档、空间预警。
- 处理历史版本、埋点、任务重启恢复。

### 13.3 P2：跨设备与高级管理

- 可选云端备份和多设备同步。
- 自动清理策略、重复音频检测、标签和收藏。
- 说话人、时间标记和音频片段级笔记引用。

### 13.4 P0 验收场景

1. 录音停止后关闭页面，重新打开录音记录，能看到并播放该录音。
2. 未点击“转为笔记”的录音在 24 小时后仍可找到，状态为“未处理”。
3. 配置本地目录后录音完成，目录中出现唯一命名的音频文件，记录显示实际归档状态。
4. 录音期间拔出移动硬盘/取消目录权限，录音仍保留应用内副本，记录显示“待归档”或“归档失败”。
5. 对同一录音先生成会议纪要、再生成学习笔记，两个版本均可查看，源音频只有一个。
6. 转写接口失败后，录音记录仍可播放，点击“重新提交”可创建新的 NoteJob。
7. 重复点击归档或处理按钮，不产生重复文件或重复任务。
8. 删除记录时，系统分别询问是否删除应用内副本和本地归档文件；取消后文件和记录均保持。
9. 现有历史音频任务没有 `recordingAssetId` 时，转化记录仍可正常打开。
10. 在 390px、768px、1440px 视口下，列表、详情和错误操作均无横向滚动或按钮遮挡。

## 14. 研发拆分建议与决策门

建议顺序：

1. 持久化模型与文件引用抽象。
2. 录音停止后的资产写入和幂等处理。
3. 录音记录查询、详情和下载。
4. 与现有 NoteJob 的关联及重新处理。
5. 本地归档服务、权限/空间检查和失败重试。
6. 设置页、批量操作、埋点和可访问性验收。

研发开始前需确认以下决策：

- 运行形态是“本地 Nest 服务 + 浏览器”还是桌面容器；这决定目录授权实现。
- P0 的归档动作是“复制并保留应用内副本”还是允许“复制成功后清理”；建议前者。
- 应用内录音资产的存储介质和服务重启后的恢复策略；不能继续只依赖进程内存。
- 默认自动归档是否开启，以及默认目录命名规则。
- 是否将所有历史上传音频回填为录音资产；建议先兼容读取，再通过用户访问时懒创建。

## 15. 结论

“配置一个电脑本地路径”可以做，但它应被定义为**用户授权后的本地归档能力**，不能代替应用内保存。真正解决“录音后没处理就找不到”的关键，是建立独立的录音资产和记录管理：录音先可靠保存，之后再随时转写、生成不同类型笔记、重试或下载。这样既能与现有录音/转写/笔记功能结合，也能避免转写任务失败或页面关闭导致源音频丢失。
